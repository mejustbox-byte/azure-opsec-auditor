# Вклад в проект

Используйте Python 3.12+ и существующий checkout. Создавайте отдельную ветку; Git worktree — только при явном запросе. Перед изменениями прочитайте [требования](docs/01-requirements.md), [модель угроз](docs/02-threat-model.md) и [матрицу правил](docs/04-check-matrix.md).

```sh
bash scripts/install.sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python scripts/check_repository.py
.venv/bin/python -m build --no-isolation
.venv/bin/python scripts/verify_distribution.py
.venv/bin/python scripts/release_assets.py
```

Для нового правила нужны синтетические положительные, отрицательные и неполные случаи, границы значений, evidence, обоснование severity, ручная remediation и ограничения. `unknown`/`not_run` нельзя превращать в `pass` при отсутствии данных. Новые поля схемы должны сопровождаться обновлением валидатора, схемы-артефакта и тестов.

Вся пользовательская документация, справка и описания правил — на русском. Команды, пути, ключи JSON, идентификаторы правил, API-имена и код сохраняйте. Изменения вносите через PR с зелёным CI; описывайте поведение и выполненные проверки, не выдавая синтетические тесты за реальные Azure/Entra-проверки.

Не добавляйте credentials, tenant exports или реальные отчёты в git/CI. Реальные лабораторные проверки требуют отдельного разрешения и test tenant; см. [процедуру](docs/05-lab-and-ci.md). Секреты не передавайте в issue/PR. Теги и опубликованные assets не передвигайте и не перезаписывайте; для нового содержимого выпускайте новую предварительную версию.
