# Evidence, отчёты и хранение

Evidence — словарь предоставленных нормализованных полей правила и их значений. Он позволяет понять условие finding, но не содержит подписанного Azure ответа и не доказывает достоверность источника. Поле `resource_ref` копирует пользовательский `id`; CLI не выполняет универсальную редакцию чувствительных данных. Даже без credentials описание прав и сетей может быть конфиденциальным.

## Минимизация и границы

В публичных fixtures разрешены только вымышленные идентификаторы и состояния. Схема запрещает дополнительные поля, однако это не DLP: секрет можно ошибочно поместить в допустимое текстовое поле. Не передавать токены, пароли, tenant exports, UPN или реальные имена ресурсов. Для реального лабораторного снимка выбирать необходимые поля, псевдонимы и корректные unavailable/skipped статусы; raw responses хранить отдельно и приватно, если они действительно нужны.

CLI читает один regular file и пишет stdout; не создаёт базу, telemetry или audit history. Оболочка, CI capture, редактор, резервное копирование и артефактный хостинг находятся вне этой границы. Перенаправление отчёта и права хранения — ответственность оператора. Схема ограничивает текстовые идентификаторы ASCII, перечисления — заданными значениями; Markdown выводит evidence через JSON в строке кода. Это не универсальная очистка произвольного Markdown: отчёт считать недоверенным содержимым.

## Хранение и retention

На POSIX перед созданием каталога использовать `umask 077`, затем каталог с правами 700 и файлы 600. Не хранить реальные отчёты в CI или GitHub releases; `reports/` и `local-data/` исключены из git, но ignored не означает зашифрованы или защищены. Проверять ACL, шифрование диска, круг пользователей и destination резервной копии. Windows ACL и удаление на Windows **НЕ ВЫПОЛНЕНО** в текущей среде; не полагаться на POSIX команды там.

Политика проекта для синтетических fixtures — хранение с исходниками. Для реальных lab evidence владелец должен до запуска задать минимальный срок, например 7 дней для исходного снимка и 30 дней для согласованного отчёта, если это соответствует его требованиям; это пример решения оператора, а не автоматический TTL продукта. CLI не удаляет файлы по сроку. Назначить владельца, дату удаления, перечень копий/backup и юридические ограничения. После истечения проверить удаление всех разрешённых копий; обычное удаление не гарантирует физическое стирание SSD/backup.

## Передача и инцидент

Передавать только по согласованному защищённому каналу; публичный issue не подходит для evidence. Для воспроизведения ошибки создавать минимальную синтетическую запись с тем же типом/ограничением. При утечке credentials немедленно отозвать/ротировать их у владельца, ограничить доступ к отчётам и следовать его incident process. Очистка git history требует отдельной координации и не заменяет отзыв credentials. Не обещать существование приватного канала проекта: [SECURITY.md](SECURITY.md) описывает фактический порядок обращения.
